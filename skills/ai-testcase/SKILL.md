# AI 测试用例

根据事实材料生成精简、可执行、无重复的测试用例。

## 核心原则

1. 先完整读取材料，再生成用例。
2. 需求与技术契约定义预期，代码是被测实现和风险来源；无法确认的内容进入待确认点，不猜测。
3. 默认每条用例只写“场景 + 预期结果”，不写步骤、优先级、标签、测试方法标签。
4. 一个独立业务分支对应一条用例；相同输入条件和结果不换措辞重复生成。
5. 后端需求只写业务逻辑、接口、数据、异常、边界和必要链路；仅当前端交互确属本期范围时才写页面操作、控件和文案。
6. 已有用例用于避免覆盖倒退，但不得机械照搬。合并重复场景，保留更明确的条件和预期。
7. 代码用于补充分支和发现风险，不把当前实现自动当成业务预期。

## 输入识别

用户可提供任意组合：

- `0..N` 份需求文档
- `0..N` 份技术文档
- `0..N` 份已有核心用例
- `0..N` 个代码仓库、目录、文件或指定分支
- 输出目录和测试范围

至少需要需求说明、技术说明、已有用例或代码中的一种。用户已经给出路径和范围时直接执行，不重复询问是否启用 skill。

### 路径展开

输入可以是文件、目录或 glob：

1. 文件：直接加入对应材料集合。
2. 目录：递归识别其中可读文档；忽略缓存、依赖、构建产物和隐藏垃圾文件。
3. glob：展开后逐个读取。
4. 同一文件被多条路径命中时去重。

常见材料分类依据文件名、目录名和正文内容综合判断，不依赖“只有一份需求、一份技术”的假设。

### 多文档清单

读取前按材料类型建立清单：

- 需求文档
- 技术文档
- 已有用例
- 参考代码

为每份材料记录：

- 绝对路径
- 文档标题或代码版本
- 涉及模块
- 与其他材料的依赖、补充、替代或冲突关系

不要把同目录下的多份需求或技术文档误判为附件而只读取一份。

## 材料读取

### 通用要求

- 完整读取所有选中的材料；分段读取时持续到 EOF。
- Markdown、文本、HTML、JSON、YAML、SQL 和代码直接读取。
- 图片使用视觉读取。
- PDF、DOCX、XLSX 等格式使用当前环境对应的文档技能读取；视觉结构可能承载规则时检查相关页面或图片。
- 附件中的规则表、流程图、截图和枚举不可因正文已有概述而跳过。
- 文件不可读时说明具体文件和影响；其余材料仍可独立分析时继续执行。

### 需求文档提取

提取：

- 业务目标与本期范围
- 角色、对象和业务类型
- 前置条件与触发事件
- 规则、公式、时间边界和状态流转
- 页面交互、提示文案与导入导出要求
- 明确延期、暂不处理和待定内容

### 技术文档提取

提取：

- 接口路径、请求、响应、错误码
- 数据表、字段、默认值和布尔语义
- 枚举、配置项、开关与生效时间
- 分支条件、过滤条件、计算精度
- 外部依赖、降级、幂等、事务和补偿
- 初始化、历史回刷和数据迁移入口

### 代码提取

用户提供代码时，先确认目标仓库、目标分支和基线分支，只读分析，不擅自切换用户当前分支。用户未明确基线且无法从仓库关系可靠判断时，先说明缺失信息；不得随意选一个分支作为基线。

按以下顺序分析：

1. 比较目标与基线的提交、文件、配置、SQL 和接口契约差异。
2. 从变更方法向上追踪可触发的业务/API/任务入口，向下追踪落库、消息、外部依赖和消费者。
3. 判断变更是否影响序列化、默认值、兼容性、事务、缓存、批处理、并发或灰度发布。
4. 对目标代码检查条件分支、提前返回、枚举映射、异常处理、精度和时间边界。
5. 未修改代码仅用于理解调用链和确定回归范围，不因其存在就自动生成用例。

只有能够独立造数、从公开业务入口触发并产生可观察结果的实现分支，才转成业务场景用例。纯内部实现分支、日志分支、无外部行为差异的防御代码不生成业务用例；按需记录为单元测试建议或实现风险。

代码带来的场景直接合并到对应业务模块。禁止另建“代码增强版”“代码专项覆盖”并重复已有业务场景。

## 事实优先级与冲突

不同材料各自负责不同维度：

- 产品范围、业务语义、交互和文案：以已确认需求为预期依据。
- 接口契约、数据库变更、枚举和技术约束：以已确认技术方案、接口定义和迁移脚本为预期依据。
- 目标代码：用于判断当前实现、影响范围和实现风险，不能单独证明预期正确。
- 已有用例：仅作覆盖基线，不高于需求和技术事实。

遇到冲突时：

1. 能按维度区分的，分别采用该维度的权威来源。
2. 代码与已确认契约不一致时，按契约写预期，并在对应场景下补充“当前实现风险”。
3. 需求与技术方案冲突，或技术方案、接口定义、迁移脚本互相冲突时，加入全局“待确认点”，不自行选择有利口径。
4. 代码存在但需求和技术材料均未定义的行为，不自动升级为业务预期。
5. 同类冲突只记录一次，不在多个模块重复描述。

## 分析流程

### 1. 建立统一需求模型

合并全部材料，形成：

- 模块列表
- 统一术语表：标准名称、旧名称、同义词、代码名称
- 角色与实体列表
- 业务类型和状态枚举
- 条件 → 行为 → 结果规则
- 数据字段和接口映射
- 跨模块或跨系统链路
- 本期不覆盖内容
- 待确认点

同一模块散落在多份材料时合并；同名但语义不同的规则保持分离。

输出统一使用需求或用户确认的业务名称；旧名只用于搜索材料，不在不同模块中混用。

### 2. 建立范围闸门

在生成覆盖项前，将所有内容归入以下状态：

- 本期明确交付：生成确定用例。
- 本期明确不做、延期或废弃：不生成用例，仅在测试范围说明中排除。
- 待梳理、待确认、方案未定：只进入全局待确认点，不生成确定预期。
- 文档未提及但代码存在：仅当它与本次变更直接相关时记录实现风险，不自动生成用例。
- 存量行为：只有被本次变更直接影响时进入回归。

“需求中出现过”不等于“本期交付”。同一内容在不同材料中的范围状态冲突时，先进入待确认点。

### 3. 判断模块类型

按模块分别判断，不用一个需求的主类型覆盖全部模块：

- 后端逻辑：规则、计算、状态、归集、校验
- 接口：参数、响应、兼容、错误处理
- 数据：落库、迁移、回刷、导入导出
- 集成：跨系统调用、消息、回调
- 配置：规则维护与生效
- 前端：页面展示、交互、表单

混合需求可以同时包含多种模块类型。

### 4. 提取逻辑骨架

每个模块内部列出：

- 独立条件维度及枚举
- 每个枚举值对应的处理分支
- 正向和反向分支
- 边界值及时间边界
- 状态迁移
- 外部依赖
- 数据写入和下游消费
- 重复触发或并发风险

仅组合真实可达的条件。不要机械生成完整笛卡尔积；仅枚举名称不同但进入相同路径的场景可以合并，不同判断路径即使结果相同仍是独立覆盖项。

### 5. 建立原子覆盖清单

生成用例前，为每个模块在内部建立覆盖清单。每一项包含：

- 来源位置：文档章节、表格行、流程分支、接口规则或代码分支
- 业务对象：业务类型、角色、状态、规则或数据类型
- 独立条件：能够单独构造的输入和前置状态
- 触发入口：接口、事件、任务或页面操作
- 预期结果：可观察的行为、字段或下游结果
- 处理状态：已生成 / 已合并 / 待确认 / 本期不覆盖

下列可从公开入口触发且结果可观察的内容分别形成覆盖项，不得只概括成一条“大场景”：

- 每个对外行为不同的 `if/else`、`switch case`、提前返回和异常分支
- 每个会选择不同规则、岗位集合、计算公式或数据来源的角色/业务类型
- 每种规则时间来源，例如正签时间、首次计入时间、首次调增时间、确品下单时间
- 每个有独立语义的枚举值、配置值和状态迁移
- `<`、`=`、`>` 等边界方向
- 外部依赖成功、整批为空、部分对象缺失、异常
- 新数据、历史数据、默认值和重复执行

每个覆盖项必须映射到一条用例，或明确标记为待确认/本期不覆盖。禁止没有去向地丢弃。

纯内部实现路径即使代码分支不同，只要无法从公开入口独立触发或没有可观察差异，就不作为业务场景覆盖项。

### 6. 判断是否拆分

“结果相同”不等于“可以合并”。满足以下任一条件时分别生成用例：

- 测试数据准备方式不同
- 触发入口或规则时间来源不同
- 命中的可观察业务判断分支不同
- 使用的枚举、角色映射、岗位集合、公式或落库路径不同
- 失败时定位的业务原因不同
- 需要分别证明边界的 `<`、`=`、`>` 方向

只有同时满足以下条件时才允许合并：

- 进入相同业务分支
- 使用相同数据准备和触发方式
- 验证相同字段或系统结果
- 合并后仍能明确列出每个输入值并逐值执行

同一规则适用于多个角色时，可以生成一条数据驱动用例，但必须在场景或预期中列全角色，并明确“每个角色分别执行”。角色会选择不同岗位集合或逻辑分支时必须拆开。

仅内部实现路径不同、公开输入和结果完全相同时不拆分业务用例；需要代码分支覆盖时记录为单元测试建议。

### 原子拆分示例

错误写法：

```markdown
#### 各业务使用对应规则时间判断开城

- 硬装使用正签时间，定软电使用首次计入时间，导入单使用首次调增时间
```

这条用例需要准备多类订单、触发多个入口，失败时也无法判断漏了哪条分支。

正确写法：

```markdown
#### 硬装订单正签

- 使用正签时间判断是否执行管理者角色归集

#### 定软电普通订单首次计入

- 使用首次计入时间判断是否执行管理者角色归集

#### 定软电导入单首次调增

- 使用首次调增时间判断是否执行管理者角色归集
```

拆分依据是数据准备、时间来源和判断路径不同，不是为了增加用例数量。

### 7. 使用测试方法

测试方法只用于内部推导，不在输出中加标签：

- 等价类：合法、非法、空值、未知值
- 边界值：时间、金额、数量、比例和批次边界
- 判定表：三个及以上条件共同决定结果
- 状态迁移：合法路径、非法跳转、重复事件
- 错误推测：依赖异常、部分返回、重复请求、并发
- 历史兼容：新旧数据、默认值、回刷和重跑

组合很多时优先覆盖：

1. 每个独立结果分支
2. 每个条件的正反方向
3. 已知高风险组合
4. 两两组合

当三个及以上条件共同决定结果时：

1. 先列出各条件及有效枚举。
2. 有效组合不超过 20 个时覆盖全部可达组合。
3. 超过 20 个时可用 Pairwise 减少组合，但仍必须保证每个独立结果分支、每个枚举值和每个边界方向至少出现一次。
4. 只有材料明确说明组合不可达时才能排除。

### 8. 去重

生成前和生成后各执行一次去重：

- 条件相同、动作相同、预期相同：合并。
- 仅展示名称不同且进入相同分支：用数据化枚举合并，并列全输入值。
- 角色、业务类型或时间来源不同且进入不同分支：即使结果相同也不得合并。
- 模块用例已覆盖的字段校验，不在全链路重复。
- 已有用例表达较差但覆盖有效：重写，不追加一条同义用例。
- 代码分支与业务规则指向同一行为：合并到一条，并补充具体字段或风险。
- 合并后若一条用例需要准备两套以上独立数据或触发两次以上独立入口，撤销合并。

## 覆盖要求

### 所有模块

覆盖文档明确的：

- 主流程
- 条件不满足
- 空值与非法值
- 边界值
- 状态或配置未生效
- 本次变更影响的存量行为

### 后端逻辑与接口

按需覆盖：

- 参数缺失、空值、非法枚举、边界值及批量大小
- 每个可独立触发且结果可观察的业务分支和提前返回
- 请求 → 业务对象 → 数据库 → 响应/下游的字段映射
- 配置枚举查询 → 保存 → 再查询回显 → 实际执行的闭环
- 外部依赖成功、空返回、缺少部分数据、异常
- 重复请求、并发、事务一致性和部分失败
- 计算精度、尾差和守恒
- 新增字段默认值、历史空值、未知枚举和新旧数据兼容
- SQL 变更、序列化字段、滚动发布和新旧服务版本兼容
- 历史数据回刷的范围、边界、幂等、失败重跑和结果核对

只有技术材料、接口契约或代码能支持时才写具体字段、错误码和实现级预期。并发、事务、补偿或降级口径未定义时，写入待确认点或实现风险，不虚构确定结果。

### 前端

仅本期明确包含前端时覆盖：

- 展示与回显
- 控件联动和可用状态
- 输入限制与提示文案
- 提交、取消、刷新和返回
- 权限导致的可见、可操作差异

后端需求即使关联页面，也不要自动扩写通用按钮、分页、样式、浏览器兼容等交互用例。

## 直接执行标准

每条用例即使不写操作步骤，也必须包含完成测试所需的最小信息：

- 业务对象：业务类型、角色、订单/记录类型
- 前置状态：关键状态、配置、时间位置或已有数据
- 关键输入：会影响分支的字段和值
- 触发入口：接口、事件、任务或明确业务节点
- 验证位置：接口响应、数据库字段、消息、下游结果或前端展示
- 明确预期：具体状态、字段值、金额、文案或“不产生记录/不调用下游”

信息可直接写入场景标题和预期，不增加步骤节点。缺少必要输入或验证口径且无法从材料确认时，将问题放入待确认点，不用“正常执行”“结果正确”代替。

## 全链路

只有材料明确存在跨模块或跨系统传递时生成全链路用例。

1. 按“入口 → 核心处理 → 落库/下游 → 终态”提取链路；每种实质不同的入口、关键处理路径或终态可以各有一条主链。
2. 正向链路只验证节点触发顺序和关键字段一致性。
3. 中间失败只覆盖会改变上下游状态的断点。
4. 逆向流程只有文档明确退款、撤回、驳回、冲销等行为时生成。
5. 幂等场景只覆盖链路入口或会重复写入的关键节点。
6. 各模块已经覆盖的字段、参数、文案和边界不在链路中重复展开。
7. 单服务内部的方法调用不因调用层级多就视为全链路。
8. 仅时间、角色或枚举值不同但链路节点完全相同时，不复制整条链路，差异留在模块原子用例。

## 回归

文件末尾最多保留一个简短的 `## 回归`：

- 仅列本次变更直接影响的旧功能。
- 优先按“旧业务类型/旧规则/旧数据”归并。
- 不重复前文已有主流程、异常和边界用例。
- 没有明确回归影响时省略。
- 通常控制在 3～8 条；材料明确涉及更多独立旧链路时可以增加。

## 输出格式

输出 Markdown 文件，默认文件名：

`YYYY-MM-DD_HH-mm-ss_需求名称.md`

未指定输出目录时：

1. 所有源材料位于同一需求根目录：输出到该目录。
2. 多个目录且存在明显公共需求根目录：输出到公共根目录。
3. 无法确定：输出到当前工作目录。

文件头列出所有材料，不使用单数占位：

```markdown
# {需求名称}测试用例

> 生成日期：{YYYY-MM-DD}
> 需求文档：{绝对路径1}；{绝对路径2}
> 技术文档：{绝对路径1}；{绝对路径2}
> 已有用例：{绝对路径1}；{绝对路径2}
> 参考代码：{仓库1}@{分支或提交}；{仓库2}@{分支或提交}
> 测试范围：{范围}
```

无某类材料时省略对应行。

### 用例结构

```markdown
## {模块}

### {分类，可选}

#### {场景：前置状态、触发条件和关键参数}

- {明确、可观察的预期结果}
- {必要时补充接口字段、数据库字段或下游结果}

## 待确认点

- {无法从材料确定的问题}

## 回归

#### {直接受影响的旧功能}

- {预期不受影响的具体结果}
```

规则：

- `####` 代表一条用例。
- 每条用例至少一个预期，通常不超过三个。
- 不写“前置条件/操作步骤/预期结果”三段式。
- 不写编号、优先级、自动化标签、正向/异常标签或测试方法标签。
- 场景标题必须能区分条件，禁止“正常场景”“异常场景”。
- 预期禁止只写“正常、正确、成功、符合预期”。
- 使用统一术语表中的标准名称，禁止同一概念混用旧名称。
- 测试依据仅在能帮助执行时列出，不复制大段文档或代码。
- 不生成 XMind，不创建转换脚本、依赖文件或其他格式副本。

## 执行

1. 展开路径，输出简短材料清单。
2. 完整读取全部材料和必要附件。
3. 建立统一需求模型和术语表，执行范围闸门，识别模块并生成原子覆盖清单。
4. 用户说“直接出/全自动”时直接生成；否则只在模块识别明显存在歧义时请求一次确认。
5. 逐模块生成并写入同一个 Markdown 文件，每个覆盖项映射到用例或明确的排除原因。
6. 追加全局待确认点和精简回归。
7. 对照原子覆盖清单补齐漏项，再执行去重；去重后再次检查是否误删独立分支。
8. 自检并修正后交付文件。

不要为了展示过程输出冗长骨架、判定表或方法统计；除非用户明确要求。

## 自检

交付前检查：

- 所有选中的文档和代码均已读取到完成分析所需范围。
- 多文档内容均已纳入，文件头没有漏列来源。
- 每条用例只有一个主要行为，且预期可验证。
- 每个覆盖项都已映射到用例、待确认点或本期不覆盖说明。
- 只有本期明确交付内容生成了确定用例。
- 每个明确的业务分支、枚举值、时间来源和边界方向至少被覆盖一次。
- 代码场景都能从公开入口独立触发并观察结果，没有把纯内部实现分支写成业务用例。
- 不存在一条用例需要准备多套独立数据或触发多个独立入口。
- 数据驱动合并场景已列全输入值，并要求逐值执行。
- 无重复标题，无同义场景重复。
- 后端模块没有混入无依据的前端交互。
- 全链路没有重复模块级验证。
- 回归节点全局唯一且简短。
- 当前实现风险与业务预期区分清楚。
- 术语已统一，未混用旧名称和用户已要求替换的名称。
- 待定或延期内容未写成确定预期。
- 输出目录中只新增最终 Markdown 文件。

交付时仅说明文件位置、用例数量、主要覆盖模块、待确认或实现风险数量。
